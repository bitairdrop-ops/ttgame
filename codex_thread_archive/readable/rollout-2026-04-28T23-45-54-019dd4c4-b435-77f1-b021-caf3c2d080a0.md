# Escalation Requests

Commands are run outside the sandbox if they are approved by the user, or match an existing rule that allows it to run unrestricted. The command string is split into independent command segments at shell control operators, including but not limited to:

- Pipes: |
- Logical operators: &&, ||
- Command separators: ;
- Subshell boundaries: (...), $(...)

Each resulting segment is evaluated independently for sandbox restrictions and approval requirements.

Example:

git pull | tee output.txt

This is treated as two command segments:

["git", "pull"]

["tee", "output.txt"]

Commands that use more advanced shell features like redirection (>, >>, <), substitutions ($(...), ...), environment variables (FOO=bar), or wildcard patterns (*, ?) will not be evaluated against rules, to limit the scope of what an approved rule allows.

## How to request escalation

IMPORTANT: To request approval to execute a command that will require escalated privileges:

- Provide the `sandbox_permissions` parameter with the value `"require_escalated"`
- Include a short question asking the user if they want to allow the action in `justification` parameter. e.g. "Do you want to download and install dependencies for this project?"
- Optionally suggest a `prefix_rule` - this will be shown to the user with an option to persist the rule approval for future sessions.

If you run a command that is important to solving the user's query, but it fails because of sandboxing or with a likely sandbox-related network error (for example DNS/host resolution, registry/index access, or dependency download failure), rerun the command with "require_escalated". ALWAYS proceed to use the `justification` parameter - do not message the user before requesting approval for the command.

## prefix_rule guidance

When choosing a `prefix_rule`, request one that will allow you to fulfill similar requests from the user in the future without re-requesting escalation. It should be categorical and reasonably scoped to similar capabilities. You should rarely pass the entire command into `prefix_rule`.

Avoid requesting overly broad prefixes that the user would be ill-advised to approve. For example, do not request ["python3"], ["python", "-"], or other similar prefixes that would allow arbitrary scripting.
NEVER provide a prefix_rule argument for destructive commands like rm.
NEVER provide a prefix_rule if your command uses a heredoc or herestring.

## [ASSISTANT]
**核心原理**

Flipbook 不是传统“网页生成器”，更像一个“AI 视觉浏览器原型”：浏览器里仍然需要一个很薄的 HTML/JS 壳，但主要内容不是 DOM、HTML、CSS 布局出来的，而是后端模型实时生成的一整张画面/视频帧，再流式传到前端显示。

可以理解成：

```text
用户输入主题 / 点击画面某处
        ↓
前端发送 query + 当前页面状态 + 点击坐标
        ↓
后端把意图转成生成任务
        ↓
图像/视频模型生成整屏视觉页面
        ↓
通过 WebSocket 把像素流/帧流传回浏览器
        ↓
前端用 canvas / video 类似方式显示
```

**它和普通网页的区别**

普通网页是：

```text
数据 → HTML → CSS 布局 → 浏览器渲染引擎 → 像素
```

Flipbook 的思路是：

```text
用户意图 → AI 模型 → 像素/视频帧 → 屏幕
```

所以它宣传的 “No HTML, no layout engine” 更准确地说是：页面主体内容不靠传统 HTML/CSS 组件布局，文字、图表、按钮感的区域甚至都只是图片里的像素。前端壳子依然存在，只是它不负责构造复杂 UI。

**交互为什么能点任意区域**

Flipbook 不是预先给每个按钮绑定链接，而是把点击位置当成语义输入：

```text
当前画面 + 鼠标坐标 + 用户原始主题
```

后端模型会推断：“用户点的是 Eiffel Tower / 电池 / 某个标签 / 图里的某块结构”，然后生成下一张更深入的视觉解释页。也就是说，点击不是打开固定链接，而是触发一次新的生成。

这也是它像“无限视觉百科”的原因：每次点击都是一次新的 prompt 分支。

**实时视频流模式**

公开资料里提到它优化了 LTX Studio 的视频模型，并通过 Modal 的 serverless GPU 跑推理，再用 WebSocket 直接向浏览器推送 1080p / 24fps 的画面流。这个模式下，体验更像“模型在直播生成界面”，而不是等一张静态图生成完再显示。

**可能的技术栈拆解**

前端大概是：

```text
React/Next 或普通 JS 壳
输入框
canvas/video 渲染区域
WebSocket 客户端
点击坐标采集
历史栈/回退/缩略图缓存
```

后端大概是：

```text
API Gateway
会话状态管理
Prompt/场景规划器
搜索或检索模块
图像/视频生成模型
GPU 推理服务
WebSocket 流媒体输出
缓存层
```

模型层可能包含两类能力：

```text
LLM：理解主题、规划页面结构、解释点击意图
图像/视频模型：把结构直接画成像素页面
```

**最大限制**

1. **文字可靠性差**：文字也是图像像素，不是 DOM 文本，容易错字、变形、不可复制。
2. **事实核验弱**：视觉解释很顺滑，但如果没有引用来源，幻觉更难察觉。
3. **延迟和成本高**：每次点击都可能触发 GPU 生成，公网爆火后很容易限流。
4. **状态保持难**：传统 UI 有明确组件状态，Flipbook 要靠模型记住上下文，复杂任务会不稳定。
5. **无障碍和 SEO 几乎天然困难**：因为主体内容不是结构化 HTML。

**一句话总结**

Flipbook 的本质是：把网页从“浏览器渲染 HTML”换成“模型直接生成屏幕像素”，再用点击坐标驱动下一次生成。它不是当前 Web 的替代品，更像是在测试未来 AI-native UI 的一种极端形态。

## [ASSISTANT]
可以。把 Flipbook 简化到本质，它不是“AI 做网页”，而是：

> **用户不再操作固定 UI，而是操作一个由 AI 实时生成、可继续追问的视觉状态。**

我会把它抽象成下一代 **AI Native UI** 的一个更实用方案：不是完全抛弃 HTML/DOM，而是采用 **“结构化状态 + 生成式视觉层 + 语义交互层”** 的混合架构。

**核心范式**

传统 UI：

```text
用户点击按钮
→ 前端组件响应
→ 状态变化
→ DOM 更新
```

AI Native UI：

```text
用户表达意图 / 点击视觉对象
→ AI 理解当前上下文
→ 生成下一步界面状态
→ 渲染成适合当前任务的 UI
```

也就是说，UI 不再是提前写死的一组页面，而是一个持续生成的“任务界面”。

**简化后的三层模型**

```text
1. Semantic State 语义状态层
   保存用户目标、上下文、数据、历史、权限、任务进度

2. Generative UI 生成界面层
   根据当前状态生成页面布局、组件、图像、解释、操作入口

3. Interaction Interpreter 交互解释层
   把用户点击、拖拽、语音、文本输入解释成下一步意图
```

不要让 AI 直接“生成整个网页像素”作为最终方案。Flipbook 很酷，但工程上太贵、太不稳定。更实际的未来方案是：

```text
AI 生成 UI schema
→ 前端用真实组件渲染
→ 需要强视觉表达时才生成图像/视频/画布
```

**推荐架构**

```text
User Intent
  ↓
AI Orchestrator
  ↓
UI Plan / JSON Schema
  ↓
Component Renderer
  ↓
Interactive UI
  ↓
User Action Events
  ↓
Intent Interpreter
  ↓
Loop
```

示例 UI schema：

```json
{
  "screen": "product_explorer",
  "goal": "解释电动车电池工作原理",
  "layout": "visual_explainer",
  "components": [
    {
      "type": "hero_visual",
      "source": "generated_image",
      "prompt": "cutaway diagram of EV battery system"
    },
    {
      "type": "hotspots",
      "items": [
        {
          "label": "电芯",
          "x": 42,
          "y": 55,
          "action": "explain:battery_cell"
        },
        {
          "label": "冷却系统",
          "x": 68,
          "y": 48,
          "action": "explain:cooling_system"
        }
      ]
    },
    {
      "type": "action_bar",
      "actions": ["继续深入", "生成对比图", "用儿童版解释"]
    }
  ]
}
```

**关键抽象**

下一代 AI Native UI 不应该是“页面”，而应该是：

```text
Scene 场景
Intent 意图
State 状态
Tool 工具
Renderer 渲染器
Memory 记忆
Guardrail 权限边界
```

用户看到的是界面，系统内部运行的是一个状态机。

**最佳实践方案**

我会把未来 AI Native UI 分成 4 种模式：

1. **Adaptive UI**
   根据用户目标动态重排界面。比如新手看到解释和建议，专家看到参数和快捷操作。

2. **Generative Canvas**
   像 Flipbook 一样生成视觉画布，但只用于解释、探索、设计、地图、知识可视化等场景。

3. **Agentic Workflow UI**
   UI 显示 AI 正在执行的任务流，用户可以中途插入、批准、撤销、调整。

4. **Conversational Control Surface**
   用户可以用自然语言改变界面本身：  
   “把这个改成表格”  
   “只显示风险项”  
   “帮我做成适合投资人的版本”

**最终形态**

一句话：

> **未来 UI 不是固定页面，而是 AI 根据用户目标即时生成的操作环境。**

工程上最合理的方案不是纯 Flipbook，而是：

```text
结构化组件为骨架
生成式视觉为表达
Agent 状态机为大脑
自然语言和点击共同作为输入
```

这会比“全像素生成网页”更稳定、便宜、可访问、可调试，也更适合真实产品落地。

## [ASSISTANT]
可以把“结构化组件”设计成 **AI 能生成、前端能稳定渲染、用户能安全操作** 的中间协议。它不是普通 React 组件，也不是纯 JSON 页面，而是 **UI Schema + 组件注册表 + 动作协议**。

**核心设计**

```text
AI 只生成结构化描述
前端只渲染已注册组件
用户动作只触发受控 action
后端/agent 决定下一步状态
```

最小架构：

```text
User Intent
  ↓
AI Planner
  ↓
UI Schema
  ↓
Schema Validator
  ↓
Component Registry
  ↓
Renderer
  ↓
Action Event
  ↓
Agent / Backend
```

**组件 Schema**

每个组件建议统一成这个形状：

```ts
type UIComponent = {
  id: string;
  type: string;
  props: Record<string, unknown>;
  actions?: UIAction[];
  children?: UIComponent[];
  visibility?: VisibilityRule;
  dataBinding?: DataBinding;
};
```

示例：

```json
{
```

我会把“结构化组件”理解成下一代 AI Native UI 的 **界面语言**：AI 不直接画死页面，也不随便生成代码，而是用一套有限但表达力强的组件语法，描述当前用户需要的操作环境。

**为什么需要结构化组件**

纯聊天界面的问题是：信息密度低、操作路径长、状态不可见。

纯生成式像素界面的问题是：不稳定、不可复制、不可访问、难调试、难做权限控制。

结构化组件的价值在中间：

> AI 负责理解和编排，组件负责稳定呈现和交互。

它让 AI Native UI 既有生成能力，又保留产品级软件需要的确定性。

**核心思想**

不要设计“页面”，而是设计“任务状态的可视化”。

比如用户说：

> 帮我分析这家公司是否值得投资。

传统 UI 会跳到一个固定 dashboard。

AI Native UI 应该动态生成一个工作台：

```text
公司概览
关键财务指标
风险摘要
竞品对比
待确认信息
下一步操作
```

这不是固定页面，而是 AI 根据任务即时组织出的组件组合。

**组件不是 UI 控件，而是认知模块**

普通组件关心按钮、卡片、表格。

AI Native 组件更应该关心“用户正在进行什么认知动作”。

例如：

```text
解释一个概念 → Explanation
比较多个选项 → Comparison
辅助做决定 → Decision Matrix
追踪任务执行 → Workflow Tracker
呈现不确定性 → Confidence View
请求用户批准 → Approval Gate
展示证据来源 → Evidence Panel
让用户调整目标 → Intent Editor
```

所以结构化组件的第一层分类，不应是视觉样式，而应是 **认知功能**。

**我建议的组件体系**

1. **Intent 组件**
   用来澄清、修改、确认用户目标。

   例如：
   “你现在想优化成本、速度，还是质量？”
   “当前目标：比较三个供应商，优先考虑交付风险。”

2. **Context 组件**
   显示 AI 当前使用了哪些上下文。

   例如：
   文件、数据源、网页、历史偏好、约束条件。

   这非常关键，因为 AI Native UI 需要让用户知道：AI 是基于什么在行动。

3. **Evidence 组件**
   展示证据、引用、依据、置信度。

   它解决 AI 幻觉和用户不信任的问题。

4. **Exploration 组件**
   用来探索知识空间。

   类似 Flipbook 的视觉画布、可点击图解、知识地图、时间线、关系图。

5. **Comparison 组件**
   用来做横向比较。

   表格只是其中一种形式，也可以是雷达图、权衡矩阵、优劣分组。

6. **Decision 组件**
   帮用户从信息走向选择。

   包括推荐排序、利弊分析、风险等级、敏感变量。

7. **Workflow 组件**
   展示 Agent 正在做什么、做到了哪一步、哪些步骤失败、哪些需要用户确认。

8. **Action 组件**
   提供可执行操作。

   例如：
   “生成报告”
   “发给团队”
   “调整预算”
   “继续深入这个方向”

9. **Approval 组件**
   所有高风险操作都经过这里。

   它不是普通弹窗，而是完整说明：
   要做什么、影响什么、会把什么数据发给谁、是否可撤销。

10. **Memory 组件**
   展示或编辑系统记住的偏好、规则和长期上下文。

   这是 AI Native UI 很容易被忽略但特别重要的一类。

**最重要的设计原则**

我觉得有 6 条。

第一，**组件必须表达状态，而不是只表达内容**。

不要只显示“结果是什么”，还要显示：

```text
AI 知道什么
AI 不确定什么
AI 正在做什么
AI 接下来准备做什么
哪些地方需要用户介入
```

第二，**组件要支持用户改写 AI 的理解**。

未来 UI 里很重要的交互不是“点击按钮”，而是：

```text
不是这个意思
换个维度比较
忽略这条数据
把风险权重调高
只看过去 6 个月
```

所以每个组件都应该有“可纠正性”。

第三，**生成式内容和确定性组件分层**。

生成式视觉适合表达：

```text
概念图
空间关系
创意方向
探索性预览
故事化解释
```

确定性组件适合承载：

```text
金额
日期
权限
法律文本
医疗信息
执行按钮
数据表格
```

这两者不能混在一起。该精确的地方必须精确。

第四，**组件动作必须可审计**。

用户点了什么，AI 为什么这么理解，触发了什么工具，产生了什么结果，都要能追踪。

这会成为 AI Native 产品的基础能力。

第五，**UI 应该从“导航”变成“推进”**。

传统软件让用户在页面之间找功能。

AI Native UI 应该持续问：

```text
为了完成你的目标，下一步最有价值的界面是什么？
```

也就是说，界面不是地图，而是工作流的当前最佳形态。

第六，**组件要能退化成自然语言**。

如果某个组件在小屏、语音、无障碍或低带宽场景下不可用，它应该能被表达成一段清晰文本。

这保证系统不是只靠华丽界面才能工作。

**一个更大的抽象**

我会把 AI Native UI 的结构化组件定义成：

```text
Goal → Context → Reasoning Surface → Decision Surface → Action Surface
```

也就是：

```text
目标
上下文
推理过程的可视化
决策过程的可视化
行动入口
```

这比“左侧菜单 + 主内容 + 右侧面板”更适合未来。

**和 Flipbook 的关系**

Flipbook 展示了一个非常激进的方向：

> UI 可以像梦一样实时生成。

但真正可落地的产品应该保留它的优点，去掉它的风险：

保留：

```text
视觉生成
任意点击探索
界面随意图变化
知识空间连续展开
```

去掉：

```text
全像素不可控
文字不可靠
交互不可审计
成本过高
状态不稳定
```

最终方案应该是：

> Flipbook 的“生成式探索感” + 结构化组件的“确定性和可执行性”。

这才是更有机会成为下一代 AI Native UI 的路线。

```text
操作：用户可以对它做什么
视图：它适合如何呈现
权限：谁能看、谁能改、谁能执行
```

```text

  - 续航
  - 成本
  - 安全风险

  - 对比不同方案
  - 生成图解
  - 找证据
  - 加入报告
```


```text
这个概念依赖什么？

这个指标和哪个业务目标相关？
```

```text
比较
验证
反驳
总结

转换视角
找来源
模拟结果
```

```text
┌─────────────────────────────┐

├─────────────────────────────┤
│ 可做什么：                   │
│ [解释] [比较] [找证据] [执行] │
├─────────────────────────────┤
│ 相关节点：                   │
│ - 电芯                       │
│ - BMS                        │
│ - 热管理                     │
│ - 安全风险                   │
└─────────────────────────────┘
```

这就是节点化 UI 的最小闭环：

```text
当前节点
→ 对它做动作
→ 产生新节点
→ 切换到新节点
```

**移动端最简单**

移动端可以直接做成三段式：

```text
顶部：当前节点
中部：AI 生成的最佳视图
底部：下一步动作
```

例如：

```text
[电动车电池]
概念节点 · 3 个来源 · 2 个待确认

它由电芯、BMS 和热管理系统组成，核心问题是能量密度、安全和成本之间的权衡。

相关节点
[电芯] [BMS] [热管理] [续航] [安全风险]

下一步
[深入解释] [生成图解] [对比磷酸铁锂和三元锂] [找资料来源]
```

用户体验非常直观：  
**你永远站在一个节点上，然后选择下一步关系。**

**最简单的交互模型**

不用先做复杂 graph。只需要：

```text
Tap node → 进入节点
Tap action → 生成视图或新节点
Back → 回到上一个节点
Pin → 收藏到工作区
```

这就够了。

核心交互是 4 个：

1. **进入节点**
   点一个概念、对象、任务、数据项，打开它的节点卡。

2. **展开关系**
   看它连接了什么：原因、结果、证据、风险、子任务、替代方案。

3. **执行动作**
   对节点做：解释、比较、验证、生成、总结、执行。

4. **保存路径**
   把探索路径保存成报告、工作流、知识库或任务清单。

**最简单的 App UI 框架**

```text
[Search / Ask]
      ↓
[Node Card]
      ↓
[Relationship Chips]
      ↓
[Generated View]
      ↓
[Action Bar]
```

这个比“聊天窗口”多一点结构，但比“知识图谱画布”简单很多。

**关键组件**

最少只需要 5 个：

```text
1. Node Card
   当前对象是什么

2. Relation Chips
   它和什么有关

3. Action Bar
   可以对它做什么

4. Generated View
   当前最合适的呈现方式

5. Breadcrumb / Path
   用户是怎么走到这里的
```

**为什么这最简单**

因为它不要求用户理解图谱。

用户只需要理解：

```text
我现在看的是这个东西
它旁边有关联的东西
我可以点进去
我可以让 AI 对它做事
```

这和现代 App 习惯很接近，只是底层从“页面导航”换成了“语义节点导航”。

把“信息网络节点化”应用到音乐 App 的 feed，最简单呈现是：

> **每条 Feed 不只是“一首歌”，而是一个音乐节点。**

一条音乐 feed 卡片应该包含：

```text
当前音乐节点
- 音频播放
- 风格标签：lofi / trap / vlog / cinematic
- 使用场景：旅行视频 / 美妆 / 游戏剪辑
- 情绪：松弛 / 高能 / 悬疑
- 生成来源：prompt / 模板 / 用户改编
- 可操作关系：相似、变奏、延长、换风格、加人声、用于视频
```

用户刷到一首歌时，不只是点赞收藏，而是可以围绕这个节点继续行动：

```text
[生成相似]
[换成日系]
[加女声哼唱]
[做 15 秒高潮版]
[匹配我的视频]
[查看同风格作品]
```

所以 Feed 从传统的：

```text
音乐列表
→ 播放
→ 点赞/收藏
```

变成：

```text
音乐节点流
→ 发现一个声音方向
→ 展开关系
→ 生成变体
→ 发布新节点
```

简要总结：

**AIMU 的音乐 feed 可以做成“可生成的声音节点网络”。**  
每条音乐都是一个节点，节点之间通过风格、情绪、场景、节奏、prompt、创作者、二创关系连接。用户在 feed 中刷到的不是静态内容，而是一个个可以继续生成、改编、使用、发布的音乐起点。

最适合的 UI 形态是：

```text
全屏音乐播放 Feed
底部显示当前音乐节点信息
右侧是收藏/分享/使用
横向 chips 展示关系节点
上滑切歌，点 chip 深挖，点 action 生成变体
```

一句话：  
**把 TikTok 式刷歌，升级成“边听边生成、边生成边分叉”的 AI 音乐节点流。**

如果仅仅作为**歌曲推荐**，就不要强调生成、发布、二创，节点逻辑要收敛成：

> **当前歌曲 → 推荐理由 → 相似方向 → 下一首**

```text
歌曲节点 = 歌曲 + 推荐理由 + 相似标签 + 操作
```

Feed 卡片可以这样设计：

```text
播放区
- 歌名 / 作者
- 封面或动态视觉
- 播放进度

推荐理由
- 因为你喜欢 lofi 鼓点
- 和你收藏的《xxx》相似
- 适合夜间工作

相似标签
- 同情绪
- 同节奏
- 同场景
- 同歌手
- 更轻 / 更燃 / 更电子

基础操作
- 喜欢
- 跳过
- 收藏
- 查看相似
```

最简单的交互闭环：

```text
听歌
→ 喜欢 / 跳过
→ 选择推荐方向
→ 下一首更准
```

这里的信息网络节点化不表现为复杂图谱，而表现为几个轻量入口：

```text
为什么推荐我？
还有哪些相似？
我想沿哪个方向继续听？
```

> **推荐型音乐 Feed 的核心不是“生成分支”，而是让每首歌成为调校下一首推荐的节点。**

## [ASSISTANT]
对，这个判断很关键。

如果是推荐型产品，用户体验的核心不是“刷得更久”，而是：

> **用户每一次交互，都让系统把他带到更好的信息节点。**

在音乐推荐里，“更好的信息节点”就是更符合当前状态的歌曲。

```text
当前歌曲
→ 用户反馈
→ 系统理解偏好
→ 推荐更好的下一首
```

所以产品不应该只问：

```text
你喜不喜欢这首？
```

而应该捕捉更细的信号：

```text
喜欢它的节奏？
喜欢它的情绪？
喜欢它适合工作？
想要更安静？
想要更有能量？
想继续听同类？
```

这样每首歌就不只是内容，而是一个“校准点”。

**最简 UX**

```text
听一首
→ 给一个轻反馈
→ 下一首更接近
```

轻反馈可以是：

```text
喜欢
跳过
更多类似
换个情绪
换个节奏
不想听这个类型
```

最终体验应该像：

> 用户不是在无限滚动，而是在一步步靠近自己想要的信息节点。

对于 App feed 来说，最好的设计不是堆很多按钮，而是在每个节点给用户 2-3 个“方向选择”：

```text
继续这个感觉
换个氛围
更适合当前场景
```

一句话总结：

> **AI Native Feed 的价值，是把推荐流从“内容消费”变成“连续的信息定位”。**
