# Escalation Requests

Commands are run outside the sandbox if they are approved by the user, or match an existing rule that allows it to run unrestricted. The command string is split into independent command segments at shell control operators, including but not limited to:

- Pipes: |
- Logical operators: &&, ||
- Command separators: ;
- Subshell boundaries: (...), $(...)

Each resulting segment is evaluated independently for sandbox restrictions and approval requirements.

Example:

git pull | tee output.txt

This is treated as two command segments:

["git", "pull"]

["tee", "output.txt"]

Commands that use more advanced shell features like redirection (>, >>, <), substitutions ($(...), ...), environment variables (FOO=bar), or wildcard patterns (*, ?) will not be evaluated against rules, to limit the scope of what an approved rule allows.

## How to request escalation

IMPORTANT: To request approval to execute a command that will require escalated privileges:

- Provide the `sandbox_permissions` parameter with the value `"require_escalated"`
- Include a short question asking the user if they want to allow the action in `justification` parameter. e.g. "Do you want to download and install dependencies for this project?"
- Optionally suggest a `prefix_rule` - this will be shown to the user with an option to persist the rule approval for future sessions.

If you run a command that is important to solving the user's query, but it fails because of sandboxing or with a likely sandbox-related network error (for example DNS/host resolution, registry/index access, or dependency download failure), rerun the command with "require_escalated". ALWAYS proceed to use the `justification` parameter - do not message the user before requesting approval for the command.

## prefix_rule guidance

When choosing a `prefix_rule`, request one that will allow you to fulfill similar requests from the user in the future without re-requesting escalation. It should be categorical and reasonably scoped to similar capabilities. You should rarely pass the entire command into `prefix_rule`.

### Banned prefix_rules 
Avoid requesting overly broad prefixes that the user would be ill-advised to approve. For example, do not request ["python3"], ["python", "-"], or other similar prefixes that would allow arbitrary scripting.
NEVER provide a prefix_rule argument for destructive commands like rm.
NEVER provide a prefix_rule if your command uses a heredoc or herestring.

有很多可能，而且最有意思的是：如果不再以 iOS/Android 的“应用-页面-按钮”模型为中心，人与 AI 的交互会从“打开 App 操作”变成“AI 持续理解环境、意图和任务”。

我会把它分成几种模式。

**1. 对话式操作系统**
用户不再打开 App，而是直接说目标：

> “帮我安排明天去台北的行程，避开下雨时段，顺便订一家适合聊天的餐厅。”

AI 负责拆任务、调用服务、确认关键决策。  
界面不是 App 图标，而是一个持续存在的“任务线程”。

核心变化：

- 用户说目标，不说步骤
- AI 维护上下文
- 所有服务变成 AI 可调用的能力模块
- 确认、撤销、权限变成最重要的系统交互

**2. 环境感知式交互**
AI 通过摄像头、麦克风、位置、时间、日程、传感器理解当前情境。

例如戴着 AI 眼镜时：

- 看到菜单，AI 自动翻译、推荐、提醒过敏食材
- 看到朋友，AI 提醒上次聊到的事情
- 走进会议室，AI 自动进入会议记录模式
- 看到设备故障，AI 指导你一步步排查

这种模式里，“用户输入”不一定是主动说话。  
环境本身就是输入。

**3. 意图流，而不是 App 流**
传统系统是：

> 打开 App → 找功能 → 输入信息 → 点确认

AI 原生系统可能是：

> 表达意图 → AI 生成行动计划 → 用户确认关键点 → AI 执行 → 用户随时纠偏

比如：

> “我要把这段视频变成一条适合小红书的内容。”

AI 会自动完成：剪辑、字幕、标题、封面、发布时间建议。  
用户只需要在几个关键节点做选择。

这会让“应用”退居幕后，变成能力供应商。

**4. 主动型 AI 助理**
不是等用户命令，而是 AI 在合适时机主动提出建议。

例如：

- “你现在离机场 45 分钟，但路况开始变差，要不要提前出发？”
- “这封邮件看起来需要今天回复，我可以帮你起草。”
- “你今天连续工作 3 小时了，下一场会议前有 12 分钟空档。”

这里最难的不是技术，而是边界感。  
AI 必须知道什么时候主动、什么时候闭嘴、什么时候只做轻提示。

**5. 多模态自然交互**
输入不只是文字或语音，而是混合的：

- 看一眼
- 指一下
- 说一句
- 做个手势
- 停顿一下
- 让 AI 读取当前画面

例如：

用户指着桌上的设备说：

> “这个怎么连不上？”

AI 通过视觉识别设备、读取状态灯、结合说明书和网络信息，直接给操作建议。

这类交互很适合 AI 眼镜、耳机、车载、机器人，而不是手机屏幕。

**6. 代理式协作**
AI 不只是回答，而是代表用户行动。

比如：

- 帮你找房、比较、联系中介、整理看房时间
- 帮你投简历、改简历、跟进邮件
- 帮你管理项目、分配任务、追踪进度
- 帮你和其他 AI 代理协商

未来可能不是“人使用软件”，而是：

> 人管理一组 AI 代理。

用户更像导演、老板、创作者，而不是按钮操作者。

**7. 记忆型人格交互**
AI 长期记住用户的偏好、习惯、关系、项目、表达风格。

例如它知道：

- 你不喜欢太正式的邮件
- 你晚上不适合做复杂决策
- 你常常先做原型再整理文档
- 你某个朋友喜欢爵士乐
- 你最近在做 AI glass 和音乐项目

这会让交互从“一次性问答”变成“长期共同生活/工作”。

但这也要求非常强的：

- 可查看记忆
- 可删除记忆
- 可关闭记忆
- 可解释为什么这样建议

**8. 空间型 AI 界面**
如果不绑定手机 OS，AI 可以存在于空间里：

- 桌面上浮动的信息层
- 墙面/投影上的任务面板
- 眼镜里的低干扰提示
- 车窗上的路线和风险标记
- 房间里多个设备共享一个 AI 状态

这不是手机里的 App，而是一个“环境界面”。

**9. 情绪与状态感知交互**
AI 根据语气、节奏、行为模式判断用户状态。

例如：

- 用户焦虑时，AI 简化选择
- 用户疲惫时，AI 延后非紧急提醒
- 用户兴奋创作时，AI 不打断，只记录想法
- 用户卡住时，AI 提供下一步建议

这类交互会非常强，但也非常危险。  
它必须避免操控用户情绪。

**10. AI 原生设备**
如果完全不基于 iOS/Android，设备形态可能也会变化：

- AI 眼镜
- AI 耳机
- AI 胸针/项链
- AI 桌面终端
- AI 家庭中枢
- AI 车载系统
- AI 机器人
- AI 投影/空间计算设备

这些设备的共同点是：屏幕不再是唯一中心。  
声音、视觉、空间、动作、上下文才是中心。

我觉得最关键的分水岭是这个：

> iOS/Android 是“应用为中心”的系统；AI 原生系统会是“意图为中心”的系统。

也就是说，未来用户可能不再想“我要打开哪个 App”，而是想：

> “我要完成什么事？”

然后 AI 决定调用哪些能力、在哪个设备上反馈、什么时候需要人确认。

- 桌面上浮动的信息层

这不是手机里的 App，而是一个“环境界面”。

**9. 情绪与状态感知交互**

**1. 低复杂度应用：AI 对话入口不是必要**
比如计算器、闹钟、扫码、天气、简单播放器。  
这些场景里，按钮和直接操作更快。硬塞聊天会降低效率。

**2. 信息量大、选择多的应用：AI 入口会很重要**
比如购物、旅游、招聘、知识库、文件管理、金融分析、医疗咨询、企业 SaaS。  
用户的问题通常不是“点哪个按钮”，而是“我该怎么选”。

**3. 创作型应用：AI 入口几乎是核心入口**
比如音乐、视频、图像、写作、设计、代码。  
因为创作意图天然模糊，用菜单很难表达：

> “更冷一点、节奏更紧、像凌晨的城市但不要太赛博。”

这种需求用传统 UI 很难承载。

**4. 工具型应用：AI 应该嵌入工作流，而不是做成客服**
比如剪辑软件、IDE、数据分析、项目管理。  
AI 最好出现在用户正在操作的位置：

- 选中一段内容后出现“解释/修改/生成”
- 当前页面支持“问这个页面”
- 表格支持“用自然语言筛选/汇总”
- 项目看板支持“总结阻塞项”

这里的 AI 不是聊天机器人，而是上下文操作层。

**5. 未来真正必要的是“可委托性”**
用户不只是问 AI，而是把任务交给 AI：

> “帮我把这 20 个候选方案筛到 3 个，并说明理由。”
>  
> “帮我回复这封邮件，但语气不要太强硬。”
>  
> “帮我检查这次发布有没有明显风险。”

这比“聊天入口”更重要。

我的结论：

> **AI 对话入口不是每个应用的必要选项，但 AI 意图入口会成为复杂应用的基础能力。**

更准确地说，未来应用不一定都要有一个“Chat”按钮，但应该考虑三个入口：

1. **全局入口**：用户随时说“我要做什么”。
2. **上下文入口**：用户对当前页面、对象、文件、图片、商品、任务发问或下指令。
3. **自动入口**：系统在合适时机主动建议、总结、提醒或执行。

如果只能选一个，我会优先做 **上下文入口**，不是独立聊天页。因为它最贴近用户当下任务，价值最高，也最不容易变成摆设。

比如音乐、视频、图像、写作、设计、代码。  
因为创作意图天然模糊，用菜单很难表达：

> “更冷一点、节奏更紧、像凌晨的城市但不要太赛博。”

这种需求用传统 UI 很难承载。

**4. 工具型应用：AI 应该嵌入工作流，而不是做成客服**
比如剪辑软件、IDE、数据分析、项目管理。  
AI 最好出现在用户正在操作的位置：

- 选中一段内容后出现“解释/修改/生成”
- 当前页面支持“问这个页面”
- 表格支持“用自然语言筛选/汇总”
- 项目看板支持“总结阻塞项”

这里的 AI 不是聊天机器人，而是上下文操作层。

**5. 未来真正必要的是“可委托性”**
用户不只是问 AI，而是把任务交给 AI：

> “帮我把这 20 个候选方案筛到 3 个，并说明理由。”
>  
> “帮我回复这封邮件，但语气不要太强硬。”
>  
> “帮我检查这次发布有没有明显风险。”

这比“聊天入口”更重要。

我的结论：

> **AI 对话入口不是每个应用的必要选项，但 AI 意图入口会成为复杂应用的基础能力。**

更准确地说，未来应用不一定都要有一个“Chat”按钮，但应该考虑三个入口：

1. **全局入口**：用户随时说“我要做什么”。
2. **上下文入口**：用户对当前页面、对象、文件、图片、商品、任务发问或下指令。
3. **自动入口**：系统在合适时机主动建议、总结、提醒或执行。

如果只能选一个，我会优先做 **上下文入口**，不是独立聊天页。因为它最贴近用户当下任务，价值最高，也最不容易变成摆设。

一句话总结：

> **上下文入口 = 用户在哪里工作，AI 就在哪里理解、建议和执行。**

**和原始 RPOW 的关系**

Hal Finney 的 RPOW 发布于 2004 年，是 Bitcoin 之前的重要数字现金实验。原始机制大致是：

1. 用户生成 Hashcash proof-of-work。
2. 服务器验证后签发 RPOW token。
3. token 可以转给别人。
4. 每次转移时，旧 token 被消耗，新 token 被签发。
5. 双花问题由可信服务器防止。

## [ASSISTANT]
Blender 在 3D 游戏里主要是 **数字内容制作工具，DCC，Digital Content Creation**。它不是游戏引擎本身，核心作用是生产游戏引擎要用的 3D 资产。

主要作用：

1. **建模**
   做角色、汽车、武器、建筑、道具、地形、树木、石头等模型。

2. **贴图和材质**
   给模型做颜色、纹理、法线、金属度、粗糙度等，让模型看起来有质感。

3. **骨骼绑定**
   给角色加骨架，让模型可以被动画驱动。比如人物走路、跑步、跳跃、攻击。

4. **动画制作**
   制作 idle、walk、run、jump、attack、death 等动作，然后导出给游戏使用。

5. **场景搭建**
   可以先在 Blender 里搭地图、关卡、灯光、物体摆放，再导出到游戏引擎。

6. **格式转换**
   把 `.blend`、`.fbx`、`.obj` 转成游戏常用格式，比如 `.glb/.gltf`、`.fbx`。

7. **资源优化**
   降面数、合并材质、压缩贴图、清理无用骨骼/控制器，减少游戏运行时压力。

在我们现在这个项目里，Blender 的作用就是：

- 下载 `.blend/.fbx` 素材
- 用 Blender CLI 转成 `.glb`
- 保留人物骨架和动画
- 清理不需要的对象
- 让 Three.js 可以加载并控制角色

简单说：

> Blender 负责“做资产”；Three.js / Unity / Unreal 负责“运行游戏”。

```

关键不是“Unity”，而是这几个条件：

1. **模型面数**
   高面数模型直接放进网页或移动端会很卡。  
   Unity、Unreal、Three.js 都一样，面数太高都要优化。

2. **贴图大小**
   4K/8K PBR 贴图很重。  
   需要压缩、降分辨率、合并材质。

3. **骨骼和动画复杂度**
   角色骨骼多、动作多、蒙皮复杂，会增加 CPU/GPU 压力。

4. **目标平台**
   - PC 高端游戏：Unity / Unreal 更合适
   - Web 展示 / 小型网页游戏：Three.js 可以，但要优化
   - 手机浏览器：必须低面数、低贴图、少骨骼
   - 影视级渲染：通常不实时运行，用 Blender/Cinema4D/Unreal 渲染

简单判断：

| 场景 | 适合方案 |
|---|---|
| 高质量 3D 游戏 | Unity / Unreal |
| 网页互动展示 | Three.js + 优化 GLB |
| 手机网页游戏 | 低模 + 压缩贴图 |
| 大型开放世界 | Unreal / Unity + LOD / streaming |
| 影视级模型 | 不直接进实时游戏，先做 retopo/LOD |

- 资源管理成熟
- 动画系统强

- 适合复杂游戏项目
