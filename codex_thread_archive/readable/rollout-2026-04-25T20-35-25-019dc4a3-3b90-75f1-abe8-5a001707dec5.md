# Escalation Requests

Commands are run outside the sandbox if they are approved by the user, or match an existing rule that allows it to run unrestricted. The command string is split into independent command segments at shell control operators, including but not limited to:

- Pipes: |
- Logical operators: &&, ||
- Command separators: ;
- Subshell boundaries: (...), $(...)

Each resulting segment is evaluated independently for sandbox restrictions and approval requirements.

Example:

git pull | tee output.txt

This is treated as two command segments:

["git", "pull"]

["tee", "output.txt"]

Commands that use more advanced shell features like redirection (>, >>, <), substitutions ($(...), ...), environment variables (FOO=bar), or wildcard patterns (*, ?) will not be evaluated against rules, to limit the scope of what an approved rule allows.

## [ASSISTANT]
一般“文生音乐”模型会拆成几层：**文本理解 → 音乐语义规划 → 音频/音乐 token 生成 → 声音合成/解码 → 后处理与安全控制**。不同公司实现细节不同，但主流架构大概绕不开这些模块。

**核心架构**

1. **文本编码器**
   
   把用户 prompt、歌词、风格、情绪、BPM、乐器、人声要求等转成条件向量。常见用：
   
   - T5 / FLAN-T5
   - CLAP / MuLan 这类音频文本联合表示模型
   - LLM 作为 prompt parser，把自然语言转成结构化音乐计划

2. **音乐表示层**
   
   文生音乐通常不会直接从文本一步生成 WAV，而是先生成某种中间表示：
   
   - **音频 token**：用 EnCodec、SoundStream、DAC 等神经音频 codec 把音频压缩成离散 token
   - **谱图 latent**：类似 Stable Diffusion，把 mel spectrogram 或 audio latent 当生成目标
   - **MIDI / symbolic tokens**：适合旋律、和弦、节奏、编曲控制，但最终还要渲染成音频
   - **多轨表示**：鼓、贝斯、和弦、旋律、人声分开生成或控制

3. **生成模型**
   
   主流有几类：

   - **Transformer / Autoregressive**
     类似 MusicLM、MusicGen、Jukebox 思路，逐步生成音频 token。优点是结构和长程依赖较好，缺点是长音频成本高。
   
   - **Diffusion / Latent Diffusion**
     类似 Stable Audio，一步步去噪生成音频 latent 或谱图。优点是音质好、并行度高，缺点是长结构、歌词对齐可能更难。
   
   - **Flow Matching / Rectified Flow**
     近几年很常见，比传统 diffusion 采样更快，适合高质量音频生成。
   
   - **Hybrid**
     先用 Transformer 生成语义/音乐 token，再用 diffusion/codec decoder 生成高保真音频。很多强模型会走混合路线。

4. **音频解码器 / Vocoder**
   
   如果生成的是 token 或 latent，需要还原成波形：
   
   - EnCodec / DAC decoder
   - HiFi-GAN、BigVGAN、UnivNet 类 vocoder
   - 自研 neural codec decoder

5. **歌词与人声对齐**
   
   这是“歌曲生成”和普通 BGM 生成最大的差别之一。需要：
   
   - 歌词分句、音节切分
   - phoneme / grapheme 表示
   - melody 与 syllable alignment
   - singing voice synthesis 或人声 codec 生成
   - 多语言发音建模

6. **音乐结构建模**
   
   一首歌不是一段随机音频，要有 intro、verse、chorus、bridge、outro。常见做法：
   
   - LLM 先生成 song plan
   - 用 section tokens 控制结构
   - 用 style / genre / tempo / key / chord progression 条件控制
   - 长上下文 Transformer 或分段生成加续写

7. **训练数据管线**
   
   这部分非常重：
   
   - 音频清洗、去噪、响度归一化
   - 切片，比如 10 秒、30 秒、2 分钟窗口
   - 提取 BPM、key、chord、instrument、genre、mood
   - 歌词对齐、ASR、声源分离
   - 去重和版权过滤
   - 生成 caption：用人工标签、弱标签、CLAP 检索、LLM 扩写

8. **安全与版权控制**
   
   商用模型通常还要做：
   
   - 训练数据授权管理
   - prompt 拦截，比如“生成某某歌手声音”
   - voice/style 相似度检测
   - 旋律查重
   - 水印或溯源
   - 内容审核

- 高质量、可授权的大规模音乐数据
- 长时结构一致性，比如 3 分钟歌不跑偏
- 歌词和旋律、人声节奏准确对齐
- 音质、混音、母带稳定

## [ASSISTANT]
Suno 的真实底层架构没有完整公开，所以只能分成两层说：

1. **公开能确认的**：Suno 是端到端 AI 音乐生成平台，模型从 v2、v3、v4 到 v5/v5.5 持续提升了歌声、结构、时长、风格遵循、remaster、cover、persona 等能力。Suno 早期开源过 **Bark**，它是 transformer-based text-to-audio 模型，能生成语音、音乐、音效等，但 Bark 不等于现在 Suno 的主力音乐模型。来源：[Suno model timeline](https://help.suno.com/en/articles/5782721)、[Suno Bark on Hugging Face](https://huggingface.co/suno/bark)。

2. **行业推断的技术路线**：Suno 很可能不是一个单模型，而是一套“歌词/结构规划 + 音乐 token 生成 + 神经音频解码 + 后处理”的系统。

```text

        ↓
```

**关键点是：它不是先写 MIDI 再找音源那么简单。**  
Suno 这种效果更像是直接学习了“成品歌曲音频”的分布，包括人声、伴奏、混音、空间感、压缩、混响、流行歌结构等。所以它生成出来会带有完整唱片质感，而不是普通 MIDI 渲染感。

它大概率用了几类技术组合：

- **LLM / 文本模型**：理解 prompt，扩写歌词，规划 verse、chorus、bridge、outro。
- **音频 tokenizer / neural codec**：把真实音乐压缩成离散 token，类似 EnCodec、SoundStream、DAC 这一路思想。
- **Transformer 或 diffusion/flow 模型**：根据文本条件生成音乐 token 或音频 latent。
- **长上下文结构建模**：让 2-8 分钟歌曲有重复副歌、段落推进、风格一致性。
- **人声建模**：歌词音节、旋律、发音、情绪、颤音、合唱、和声一起生成或联合控制。
- **后处理模型**：remaster、extend、cover、stem separation、replace section 等功能可能依赖额外的编辑/转换模型。

Suno 最难的地方不是“生成声音”，而是同时做到：

- 歌词能唱出来
- 旋律像歌
- 段落像完整歌曲
- 人声和伴奏同步
- 混音听起来像成品
- 风格提示能被遵守
- 用户几秒内就能拿到结果

所以它的护城河主要在三块：**大规模音乐数据与标注、长时音频生成模型、产品级音乐编辑管线**。

可以把 Suno 理解成音乐版的“文生视频系统”：表面是一个 prompt 框，底下其实是规划器、生成器、解码器、编辑器、审核器、混音器一起工作。

Suno 这种效果更像是直接学习了“成品歌曲音频”的分布，包括人声、伴奏、混音、空间感、压缩、混响、流行歌结构等。所以它生成出来会带有完整唱片质感，而不是普通 MIDI 渲染感。

它大概率用了几类技术组合：

- **LLM / 文本模型**：理解 prompt，扩写歌词，规划 verse、chorus、bridge、outro。
- **音频 tokenizer / neural codec**：把真实音乐压缩成离散 token，类似 EnCodec、SoundStream、DAC 这一路思想。
- **Transformer 或 diffusion/flow 模型**：根据文本条件生成音乐 token 或音频 latent。
- **长上下文结构建模**：让 2-8 分钟歌曲有重复副歌、段落推进、风格一致性。
- **人声建模**：歌词音节、旋律、发音、情绪、颤音、合唱、和声一起生成或联合控制。
- **后处理模型**：remaster、extend、cover、stem separation、replace section 等功能可能依赖额外的编辑/转换模型。

Suno 最难的地方不是“生成声音”，而是同时做到：

- 歌词能唱出来
- 旋律像歌
- 段落像完整歌曲
- 人声和伴奏同步
- 混音听起来像成品
- 风格提示能被遵守
- 用户几秒内就能拿到结果

所以它的护城河主要在三块：**大规模音乐数据与标注、长时音频生成模型、产品级音乐编辑管线**。

可以把 Suno 理解成音乐版的“文生视频系统”：表面是一个 prompt 框，底下其实是规划器、生成器、解码器、编辑器、审核器、混音器一起工作。

| 版权/合规 | MiniMax 页面宣称生成音乐 royalty-free，可商用，仍需看地区和具体条款 | Suno 正在与音乐产业合作，但训练/版权争议和平台条款仍需仔细评估 |

**MiniMax 的能力边界**

MiniMax 更适合这些场景：

- 你要在自己的产品里加“AI 生成歌曲/BGM”
- 你需要明确的 API、任务参数、返回格式
- 你要生成中文歌、短视频 BGM、游戏音乐、广告歌、主题曲
- 你要让用户输入歌词、选择风格，然后直接生成 MP3/WAV
- 你要做 cover 风格迁移或纯音乐生成
- 你要控制 BPM、key、结构标签、输出格式、流式返回

它的边界也比较明显：

- 目前更像“生成一次完整成品”，不是专业 DAW 级逐轨编辑系统
- 人声 persona、自定义歌手模型、长期个人风格记忆这类能力，公开 API 层不如 Suno v5.5 产品线突出
- 对复杂音乐制作细节的可控性仍有限，比如精确和弦、小节级编曲、指定某个乐器在第几拍进入
- 生成效果稳定性要靠大量 prompt/歌词模板调优

**Suno 的能力边界**

Suno 更适合这些场景：

- 个人创作者快速做完整歌曲 demo
- 想要更强的“像一首歌”的整体感：人声、旋律、段落、情绪、混音
- 需要长歌、风格探索、remix、extend、persona/voice 方向能力
- 想围绕某个创作者的声音、风格、审美持续创作
- 不急着深度接入自己的后端系统

它的边界是：

- 没有官方公开生成 API，所以不适合作为严肃产品后端直接依赖
- 第三方 Suno API 多数是包装/逆向/代调用，稳定性、合规、账号风险都要考虑
- 细粒度工程控制不透明，难保证生成时长、格式、并发、SLA
- 对企业产品来说，版权、授权、声音克隆、训练数据来源等问题需要法务确认

**实际怎么选**

做 **面向用户的 AI 音乐 App / 游戏配乐 / 视频工具 / SaaS 功能**：优先 MiniMax。  
做 **音乐人创作、demo、个性化声音、风格探索**：优先 Suno。  
做 **正式商业产品**：MiniMax 更容易走通工程链路。  
做 **追求成品歌的惊艳度和创作体验**：Suno 往往更强。

我会把它们这样定位：

```text
MiniMax = API-first 的音乐生成模型
Suno    = Creator-first 的 AI 音乐平台
```

如果你要做自己的文生音乐产品，比较现实的架构是：**MiniMax 做主 API 后端，Suno 做效果标杆和人工创作参考**，不要把 Suno 第三方 API 放在核心生产链路上。

- 没有官方公开生成 API，所以不适合作为严肃产品后端直接依赖
- 第三方 Suno API 多数是包装/逆向/代调用，稳定性、合规、账号风险都要考虑
- 细粒度工程控制不透明，难保证生成时长、格式、并发、SLA
- 对企业产品来说，版权、授权、声音克隆、训练数据来源等问题需要法务确认

**实际怎么选**

做 **面向用户的 AI 音乐 App / 游戏配乐 / 视频工具 / SaaS 功能**：优先 MiniMax。  
做 **音乐人创作、demo、个性化声音、风格探索**：优先 Suno。  
做 **正式商业产品**：MiniMax 更容易走通工程链路。  
做 **追求成品歌的惊艳度和创作体验**：Suno 往往更强。

我会把它们这样定位：

```text
MiniMax = API-first 的音乐生成模型
Suno    = Creator-first 的 AI 音乐平台
```

如果你要做自己的文生音乐产品，比较现实的架构是：**MiniMax 做主 API 后端，Suno 做效果标杆和人工创作参考**，不要把 Suno 第三方 API 放在核心生产链路上。

## [ASSISTANT]
要把音乐生成 API 封装成“大量用户并发生成歌曲”的产品，核心不是直接前端调 MiniMax，而是做一个**异步任务队列系统**：用户提交任务，你排队、限流、调用上游、存储结果、通知用户。

**推荐架构**

```text
Web / App
  ↓
你的后端 API
  ↓
鉴权、额度、风控、参数校验
  ↓
任务表 Job DB
  ↓
队列 Queue
  ↓
Worker 集群
  ↓
MiniMax / ElevenLabs / 其他音乐 API
  ↓
对象存储 S3/R2/OSS
  ↓
生成结果回写 DB
  ↓
前端轮询 / WebSocket / Push 通知
```

**不要同步等待生成**

音乐生成通常几十秒到几分钟。前端请求不要一直挂着等结果，应该这样：

1. 用户点击生成
2. 后端创建 `job_id`
3. 立即返回：

```json
{
  "job_id": "song_123",
  "status": "queued"
}
```

4. Worker 后台生成
5. 前端轮询：

```http
GET /api/music/jobs/song_123
```

6. 完成后返回：

```json
{
  "status": "completed",
  "audio_url": "https://cdn.example.com/song_123.mp3"
}
```

**关键模块**

1. **任务队列**

常见选择：

- Redis + BullMQ：Node.js 最方便
- Celery + Redis/RabbitMQ：Python 常见
- Sidekiq：Ruby
- Cloud Tasks / SQS / PubSub：云原生

如果你做 Node/Next.js，我建议：

```text
Next.js / Express API
+ PostgreSQL
+ Redis
+ BullMQ
+ Worker
+ S3/R2
```

2. **并发控制**

你需要控制三层并发：

```text
用户级并发：每个用户同时最多生成 N 首
全局并发：整个系统同时最多跑 M 个任务
上游并发：MiniMax API 同时最多请求 K 个
```

比如：

```text
free 用户：同时 1 个任务
pro 用户：同时 3 个任务
global worker concurrency：20
MiniMax provider concurrency：10
```

3. **额度与计费**

每次生成前先扣额度，失败再退回，或者先冻结额度。

```text
queued      创建任务，冻结 1 credit
processing 任务开始
completed  扣除 credit
failed     退回 credit
```

任务状态建议：

```text
queued
processing
succeeded
failed
canceled
expired
```

4. **多供应商封装**

不要把业务代码直接写死 MiniMax。做一个 provider 层：

```ts
interface MusicProvider {
  generate(input: GenerateMusicInput): Promise<GenerateMusicResult>
}
```

然后实现：

```text
MiniMaxProvider
ElevenLabsProvider
MubertProvider
FallbackProvider
```

这样以后可以：

- MiniMax 做主生成
- ElevenLabs 做高质量套餐
- Mubert 做 BGM
- 某个 API 超时后切备用
- A/B 测试不同模型

5. **结果存储**

假设 **DAU 10 万**，音乐生成并发体量主要取决于两个数：

```text
每日生成歌曲数 = DAU × 生成渗透率 × 人均生成首数
所需平均并发 = 每日生成歌曲数 × 单首生成耗时 / 86400
峰值并发 ≈ 平均并发 × 3~10
```

假设单首生成耗时 **60-180 秒**，常见估算如下。

| 场景 | 生成渗透率 | 人均生成 | 日生成量 | 平均并发 | 峰值并发 |
|---|---:|---:|---:|---:|---:|
| 轻度 | 5% | 1 首 | 5,000 首/天 | 3-10 | 20-80 |
| 中等 | 10% | 2 首 | 20,000 首/天 | 14-42 | 80-300 |
| 活跃 | 20% | 3 首 | 60,000 首/天 | 42-125 | 250-800 |
| 爆发 | 30% | 5 首 | 150,000 首/天 | 104-313 | 600-2,000 |

所以 **10 万 DAU 的音乐生成产品**，比较现实的工程预估是：

```text
普通日：几千到几万首/天
活动日：几万到十几万首/天
后端生成峰值并发：100-1000+
```

如果你的产品核心就是“来这里生成歌”，我会按这个档位设计：

```text
日生成量：20,000-60,000 首
平均生成并发：20-100
峰值生成并发：200-800
任务队列容量：至少 50,000-200,000 jobs/day
```

如果当前 Token Plan 是：

**推荐容量设计**

第一版可以按这个目标：

```text
用户提交 QPS：50-300/s
生成任务入队 QPS：1-10/s
实际上游生成并发：50-200
任务完成吞吐：2,000-20,000 首/小时
队列可积压：30-60 分钟
```

如果单首平均 2 分钟，上游并发 200，大概吞吐是：

```text
200 并发 × 60 / 2分钟 = 6,000 首/小时
≈ 144,000 首/天满载
```

比较健康的做法是：**前端允许 10 万人同时用产品，但真正生成任务必须排队、分级、限流。**

例如：

```text
免费用户：每天 1-3 首，同时 1 个任务
付费用户：每天 20-100 首，同时 2-5 个任务
企业用户：独立队列
全局 MiniMax 并发：按商务额度动态调整
```

一句话：
